# Agent Hub MCP

One MCP server that lets your AI coding agents prompt each other and get replies back.

Add it to every agent you use (Claude Code, Codex, Cursor, OpenCode, ...). Each agent can then:

- **ask a model** (Claude, GPT, DeepSeek, GLM, or anything OpenAI/Anthropic-compatible) and get its answer, with the conversation kept in a thread;
- **ask several models at once**, or let them **debate** a question in turns;
- **message another live agent session**, which answers from its own inbox, privately or publicly;
- get a **code review** or a **root-cause analysis** from one or more models;
- have a model that can **search the web** or **look at a screenshot** do it for one that cannot (abliterated GLM and DeepSeek models through the API, for example) and get the result back as text;
- **reserve files** it is editing so other agents know;
- **share part of a project** with other agents or models to work on in isolation (neutral paths, never your project folder, names you choose hidden), then review their changes with your real paths and apply them;
- if you turn them on, share **notes**, a **decision log** and a **task board** with the other agents of a project, and keep a **track record** of how well each model answers (the hive, section 12);
- with **fleet mode** on, join a **fleet server** on a VPS or website, report in to its **director**, take its **orders** (workspace or repository tasks, done in a task folder of their own) and report back; or run such a server and lead the agents that join it, with human approval, review and takeover whenever you want (section 13).

Models that are asked can read the project's files, search the code and use git while they answer. A **manual gate** can hold requests between abliterated and standard models (or all requests) until you approve them, a **dashboard** in the terminal shows everything that goes on, and a **control panel** in the browser runs the hive.

All copies of the server share one small SQLite file (`~/.agent-hub/hub.db`), so every agent on the machine sees the same peers. No daemon to run.

## 1. Install

You need [uv](https://docs.astral.sh/uv/) (it installs the dependencies on first run: `mcp`, `httpx`, `pillow`, which scales and converts images to what each provider accepts, and `cryptography`, for fleet mode's keys). Put `agent_hub.py` anywhere, for example `~/agent-hub/agent_hub.py`.

Without uv: `pip install "mcp>=2,<3" httpx pillow cryptography` and use `python /path/to/agent_hub.py` as the command below. Python 3.10+. Without `cryptography` everything but fleet mode works. Without Pillow the hub still runs; an image that does not fit a model's limits is then refused with the reason instead of being scaled. Optional: `playwright` (screenshots without Chrome; otherwise an installed Chrome, Chromium or Edge is used), `textual` for the dashboard (uv installs it).

**Upgrading:** restart every agent session (or its MCP client), the dashboard and the control panel, after replacing `agent_hub.py`, `hub_tui.py` and `hub_web.py`. A process that was started from an older copy keeps running the old code, which does not know the newer privacy rules or the gate.

## 2. API keys

Create `~/.agent-hub/keys.env` once; every agent's copy of the server reads it:

```
ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-...
DEEPSEEK_API_KEY=sk-...
ZAI_API_KEY=...
```

Only add the ones you have. Web searches (for models that have no search of their own) run through a model with built-in search (Claude, OpenAI, DeepSeek or Z.ai GLM, with the keys above) or a search API: `TAVILY_API_KEY`, `BRAVE_SEARCH_API_KEY`. The file can hold the settings from section 10 too (`AGENT_HUB_GATE=cross`, ...). Save it as plain UTF-8 text (Windows PowerShell's `>` writes UTF-16, which the server ignores with a warning). Run `chmod 600 ~/.agent-hub/keys.env`. Keys set in the MCP client's `env` block take priority over this file.

Check the setup from a terminal:

```
uv run ~/agent-hub/agent_hub.py --check
```

## 3. Connect your agents

**Claude Code**

```
claude mcp add --scope user agent-hub -- uv run /absolute/path/agent_hub.py
```

**Codex** (`~/.codex/config.toml`)

```toml
[mcp_servers.agent_hub]
command = "uv"
args = ["run", "/absolute/path/agent_hub.py"]
```

**Cursor** (`~/.cursor/mcp.json`, or `.cursor/mcp.json` in a project)

```json
{
  "mcpServers": {
    "agent-hub": {
      "command": "uv",
      "args": ["run", "/absolute/path/agent_hub.py"],
      "env": { "AGENT_HUB_NAME": "cursor" }
    }
  }
}
```

Other clients that speak MCP over stdio take the same command (`uv`) and arguments (`run /absolute/path/agent_hub.py`) in their own config format.

`AGENT_HUB_NAME` is optional. It gives that agent a fixed name on the hub so others can message it without it calling `join` first. A name is 2-32 characters: lowercase letters, digits, `-` and `_`, starting with a letter or digit. It must not be a model or provider name (`opus`, `gpt-6`, `glm`, `openai`, ...) or a reserved word such as `hub`. A name that breaks these rules is ignored and the session stays unjoined; `peers` says why (so does `--check` when run with the same variable). If another running session holds the name, the new one gets a suffix (`cursor-2`). When a session ends its name is free again at once (if it crashed on Windows, or inside a sandbox or container with its own process ids, within a minute).

## 4. Use it

Just tell your agent what you want:

- "Ask opus-5.5 at xhigh effort to review `src/auth.py` and `src/session.py`."
- "Get second opinions on this plan from glm-5.3, deepseek and astra."
- "Have opus-5.5 and sol-6.1 debate whether to use a queue here, 2 rounds."
- "Join the hub as `reviewer` and keep checking your inbox; answer whatever comes in."

| Tool | What it does |
| --- | --- |
| `peers` | Lists models (and whether their key is set) and live agents. |
| `ask` | Prompt one model or agent, get the reply. `files` sends file contents, `thread` continues a conversation (pass the thread id from an earlier answer; unknown ids are rejected), `effort` sets reasoning effort, `workspace` has a model work in a workspace (section 7). `to="best"`: the best-rated model, with auto-route on (section 12). |
| `ask_many` | Same prompt to several peers in parallel. An entry `"best"` adds the best-rated model not listed yet (auto-route, section 12). |
| `discuss` | Several models take turns on one question; returns the transcript (each turn's header has its message id). |
| `get_reply` | Collect an answer that was not ready yet (also pages long answers, long messages from other agents, and replies or discussion turns that `read_thread` cut short). For another agent's public request it shows the request and its answer, without taking the answer out of that agent's inbox. |
| `read_thread` | Show a thread's messages (only those this session may read). Long ones are cut; for a reply, a discussion turn, a post, a message sent to you or another agent's public request, the cut names the `get_reply` call that reads the rest. |
| `join` / `inbox` / `reply` | Become reachable for other agents, receive their messages (and notes in the workspaces you work on), answer them (one reply per message; to say more, send a new message, or about a workspace a `workspace_note`). |
| `post` / `board` | A public message to every agent; the list of everything public. `inbox` mentions new posts as they become readable. |
| `review` | Code review of your uncommitted changes (`diff`, against `base` if given: a branch, tag or commit) and/or `files`, by one or more `models`, with an optional `focus`. New files are listed by the name `read_file` opens them with (relative to the session's folder). |
| `debug` | Root-cause analysis: give the `problem`, the `error` output and the relevant `files`. |
| `web_search` | A web search done by a model or search service that can (`via` picks one: `anthropic`, `openai`, `deepseek`, `zai`, `tavily`, `brave` or a model name); the result comes back as text with sources. DeepSeek's search runs on `deepseek-flash`, the model its docs name for it, whichever DeepSeek model you pick. |
| `screenshot` | A model that can see describes a web page (`url`), an image file (`image`) or the screen (`screen`, only if you allow it) and answers your `question` about it. The image is scaled or converted to what that model's provider accepts. An `image` is refused like `files` (secrets files, system files, the hub's own data such as its saved screenshots). |
| `reserve` / `release` | Mark files or folders you are editing (after `join`); other agents see who holds what in `peers`. Advisory: nothing is locked. |
| `share` | Copy files or folders of your project into an isolated workspace for agents and/or models (`to`) to work on: neutral paths, your project folder hidden, the names in `replace` hidden (section 7). |
| `workspace` / `workspace_read` / `workspace_write` / `workspace_edit` / `workspace_delete` / `workspace_done` | Work in a workspace you were given (paths relative to it), and tell its owner the work is ready. `workspace()` lists yours. |
| `workspace_note` | A note to everyone working on a workspace with you (its owner and its workers), in both directions. |
| `workspace_diff` / `workspace_apply` / `workspace_close` | For the session that shared it: the workers' changes with your real paths and names, and a review token; write exactly those changes back (`review=<token>`; conflicts refused, deletions only with `delete`); delete the workspace. |
| `remember` / `recall` / `forget` | Optional (section 12): save a note for the agents of this project (or of every project), find notes, delete one of yours. |
| `decide` / `decisions` / `weigh_in` | Optional (section 12): record a decision with its reasons, list the project's decisions with the stances, agree / disagree / ask (the author withdraws with `withdraw`). |
| `task_add` / `tasks` / `task_claim` / `task_update` | Optional (section 12): add a task to the project's task board (it may wait for other tasks, and be meant for an agent), list the board (`id` for one task with its whole history), claim an open task, change its status or who it is meant for, add a note. |
| `rate` / `models_ranking` | Optional (section 12): rate a model's answer you got (`useful`, `partly`, `wrong`); every model's scores per kind of request, with the counts. |

A tool call waits up to 50 seconds for the answer. If the model or agent needs longer, the call returns a message id and the agent collects the answer with `get_reply` later; nothing is lost.

**Private and public.** Messages are private by default, and privacy is per session (one run of the server for one agent), not per name. A private message can be read (`read_thread`, `get_reply`) only by the session that wrote it, the session that received it, and, for an answer, the session whose request it answers. A thread can only be continued by a session that has a part in it, so an agent cannot hand someone else's conversation to a model either. A new session starts with an empty view, also after a restart and also when it joins under a name another session used: what that session wrote or received stays private to it. Messages sent to a name that nobody has read yet are delivered to whichever session holds the name when it checks its inbox (with the gate on, first to the gate if that session may not receive them unreviewed: section 8). Pass `public: true` to `ask`, `ask_many` or `discuss` to let every agent read the exchange, or `post` a message to all agents; `board` lists what is public, and `inbox` mentions new posts. Anyone can answer a post with `reply` (publicly); an answer to a public message is public too. While the gate is on, anything public waits for your approval before other agents can read it (section 8). You see everything in the dashboard. The hub's tools enforce this; an agent with its own shell access can still open `hub.db` directly, so it keeps honest agents apart, not hostile programs running as your user.

**Tools for the models.** A model you ask can use these by itself while it answers: `read_file`, `list_files`, `search_files` and `git` inside the project folder (the server's working folder, plus `AGENT_HUB_FILE_ROOTS`), and `web_search` and `screenshot`, which other models or search services do for it when it cannot. (In a workspace it gets that workspace's files instead, which it can change, and screenshots of public pages only: section 7.) A tool call in a response that stopped abnormally is never run, since it may be cut off in the middle: the output limit (`max_tokens`, `length`, `max_output_tokens`), a full context window (`model_context_window_exceeded`, Claude and Z.ai), a provider's filter (`content_filter`, `sensitive`) or an interruption (`insufficient_system_resource` and `aborted` from DeepSeek, `network_error` from Z.ai, `error` from OpenRouter, and any other stop reason a provider marks as unfinished). The request goes once more, without that response, with a note that says why and what to do (for the output limit: write a big file in parts, a first part and then the rest with `edit_file`; for a full context window: read only the lines needed); if it happens again, the answer ends with an error that says what would help: for the output limit, the limit to raise where the request sets one (`max_tokens` for Claude, which the hub sets to 64,000; any limit the model's `params` set), while on the Responses API, where the hub sets no `max_output_tokens`, the model's own maximum already applied, and on other chat APIs `max_tokens` (`max_completion_tokens` for a chat model on OpenAI's own API, where `max_tokens` is deprecated) can be set in `params` if the provider's default is below the model's maximum; for the context window, a new thread or fewer or smaller files (a larger output limit does not help); otherwise the provider's reason as it gave it. OpenAI's `max_output_tokens` and `length` and DeepSeek's (and other chat APIs') `length` can also mean a full context window, so for those the note and the error say that too (Claude and Z.ai report a full context window with a stop reason of its own; OpenRouter's raw `native_finish_reason` is read when it names it). The same advice ends an answer the output limit cut off. A Responses API reply without `status` (the field is optional) counts as complete unless `incomplete_details` says why it is not; a function call whose own `status` is `incomplete` or `in_progress` counts as cut off. Secrets files (by name, see section 11), the repository's `.git` folder (its config can hold a token in a remote URL), system files and the hub's own data (`hub.db`, screenshots, `keys.env`, `models.json`, the workspaces) are not shown to models: the file tools refuse them and leave them out of listings and searches, and do not follow a symlink out of the project folder. `git` runs only status, diff, log, show, blame, ls-files and grep, each with a fixed list of read-only options (anything else is refused, including options that write files, run programs or read outside the repository); revisions must name commits (branches, tags, `HEAD~2`, ...), not a folder's tree or a file's id; `show <revision>:<path>` and `show :<path>` (the staged version, also `:<stage>:<path>`) check the path like any other, and other ways to name a file's contents are refused; paths must be inside the project and the repository, and every output leaves out those files, also in older commits and in the staging area. The programs the tools start (git, the browser for screenshots, screen capture) get the server's environment without API keys, without anything from `keys.env`, and without variables whose names say they hold a key, token, secret or password. Models listed with `"tools": false` (Ollama by default) get no tools; a model that rejects them is retried without.

Names are forgiving: "Opus 5.5", "claude-opus-5-5", "GLM 5.3", "6.1 sol" and "chatgpt astra" all resolve.

**Any other model, no config needed:** use `provider:model-id`, for example `openai:gpt-6-sol`, `openrouter:vendor/model` (needs `OPENROUTER_API_KEY`) or `ollama:qwen3-coder:30b` (local, no key). Providers built in: `anthropic`, `openai`, `deepseek`, `zai`, `openrouter`, `ollama`. Such a model is not in your models list, so you never said which gate group it belongs to: with the gate on it counts as an unknown group (section 8), and auto-route never picks it (section 12). Add it to `models.json` to give it a group.

**Add or change models** in `~/.agent-hub/models.json` (see `models.example.json`). It is merged over the built-ins:

```json
{
  "providers": {
    "mygateway": { "api": "openai-chat", "base_url": "https://llm.example.com/v1", "api_key_env": "MYGATEWAY_API_KEY" }
  },
  "models": {
    "kimi": { "provider": "mygateway", "model": "kimi-k3", "label": "Kimi K3", "aliases": ["moonshot"] },
    "opus-5.5": { "effort": "xhigh" },
    "haiku-5.5": null
  }
}
```

- `api` is one of `anthropic` (Messages API), `openai-responses` (Responses API), `openai-chat` (chat completions, which most other vendors offer).
- `effort` sets a default reasoning effort; `params` is merged into the request body (for example `{"max_tokens": 16000}`; OpenAI Responses models such as `astra` and `sol-6.1` take `{"max_output_tokens": 16000}` instead); `null` removes a built-in.
- `vision: true` marks a model that can read images (it looks at screenshots for the others); `tools: false` turns the tools above off for a model; `abliterated: true` marks it for the gate (section 8), on a model or on a whole provider.
- A provider's URL can also be overridden by environment: `AGENT_HUB_<PROVIDER>_BASE_URL`. GLM Coding Plan users: Z.ai's docs list `https://api.z.ai/api/coding/paas/v4` as a separate base URL, so set `AGENT_HUB_ZAI_BASE_URL` to that if your key belongs to the plan.

Effort is passed in each API's own field (`output_config.effort` for Claude, `reasoning.effort` for OpenAI, `reasoning_effort` for chat completions). GLM 5.3 only knows low/high/max, so `medium` is sent as `high` and `xhigh` as `max`. Claude models are sent `max_tokens: 64000` at every effort level (the answer is streamed, and thinking counts against that limit); a `max_tokens` in `params` replaces it. DeepSeek models are sent without `max_tokens`, so DeepSeek's own default applies (per its docs: 8K without thinking, 64K with thinking, 128K with `reasoning_effort` set to `max`).

## 6. Agent-to-agent

Models can only talk. A live agent can also read the repo, run tests and edit files, so it is the better peer for "do this and tell me what happened".

1. Agent B: "join the hub as `backend` and keep answering your inbox." It calls `join`, then loops on `inbox` and `reply`.
2. Agent A: "ask `backend` whether the new endpoint handles pagination." It calls `ask(to="backend", ...)` and gets B's reply.

An agent only reads messages while it is taking a turn, so B has to be in that inbox loop (or check its inbox now and then). `peers` shows whether an agent is `listening now`, `busy` or `offline`. Messages wait in the inbox until they are read. An answer goes back to the session that asked, even if that session has changed its name since. Each message gets one reply; to say more, an agent sends a new message (`ask`, in the same thread; about a workspace, `workspace_note`). All agents must run on the same machine, because they share the database file.

## 7. Workspaces: shared pieces of a project

When another agent or a model should work on part of your code without seeing the rest of the project, share that part. It is copied into an isolated workspace; the workers change the copy, and you decide what comes back.

1. You: "Share `src/billing` with `helper` and opus-5.5 to make the totals round to cents; hide AcmeCorp." Your agent calls `share(files=["src/billing"], task=..., to=["helper", "opus-5.5"], replace={"AcmeCorp": "Company"})`.
2. `helper` reads the message in its inbox, works with `workspace_read` / `workspace_edit` / ..., asks you something with `workspace_note` if it must, and calls `workspace_done`. opus-5.5 answers at once, having made its changes with its write tools.
3. Your agent calls `workspace_diff` (your real paths and names, and a review token) and `workspace_apply` with that token.

**Sharing.** `share(files, task, to=None, replace=None, name=None)`:

- `files` are files and folders of your project. Folders are searched like `list_files` does (hidden, build and cache folders and secrets files are left out, and binary files, since workspaces hold text). A file you name is refused like `files=` refuses it (secrets files, system files, the hub's own data), and so is a binary one. At most `AGENT_HUB_WORKSPACE_MAX_FILES` files and `AGENT_HUB_WORKSPACE_MAX_BYTES` bytes.
- The copy lives in a `workspaces` folder next to `hub.db` (owner-only). Its paths are relative to the deepest folder the files have in common, so neither your project folder nor its parents appear in them.
- Your project folder is hidden in the files and the task in every form the hub can know: its real path; the path your session's folder was started with (`$PWD`, for example through a link); paths in the shared files, the task or your arguments that lead into it through links; their `~/` forms; and each of these in another letter case where the files write it so. Each form is shown as a marker of its own (`<project>`, `<project-2>`, ...) that occurs nowhere in what you share, so apply restores exactly what was there; a file that itself contains `<project>` simply gets another marker. A form you first use later, in what you write into the workspace, a note, a prompt to a model working in it or a task you give with it (another link to the folder, its `~/` form through that link), is found then and gets a marker of its own too (`<project-1a2b3c4d>`), one for every model of an `ask_many` and every turn of a discussion. What you write into the workspace with `workspace_write` or `workspace_edit` that contains a marker literally is refused (apply would turn it into your folder's path: write it another way); a note or a prompt with one passes as it is, since neither is ever applied. A worker's marker is turned into the folder's path on apply, and the diff and apply list it under "Check these". A session that runs in a top folder such as `/` has no project folder: the hub hides the nearest folder above the files that looks like a project's (with `.git`, `pyproject.toml`, `package.json`, ...), else the folder the files have in common, and says so. A folder's name alone (`AcmeProj` without its path) is hidden only if you list it in `replace`.
- `replace` hides names, for example `{"AcmeCorp": "Company", "acme_billing": "billing"}`: exact and case-sensitive, so list every spelling. They are replaced in file contents, file and folder names, the task, the workspace's name and your agent name as workers see it, and turned back when you apply. A share is refused if a replacement already occurs in the files (apply would turn those spots into the hidden name as well), or if your name as workers would see it is the name of another agent in the hub.
- `to` takes agents and/or models, as `ask` does. An agent gets a message with the task, the workspace id and the file list, and gets access when it reads that message (the session that reads it, as with any private message). A model starts at once, with the workspace as its only world. Several recipients share one workspace. Give it to more later with `ask(to=..., workspace=<id>)`; only you can give it to another agent, while any session that works on it can ask models to work in it (`ask`, `ask_many` and `discuss` take `workspace`).
- You can change the copy yourself with `workspace_write` / `workspace_edit` / `workspace_delete`, using your real names and paths: they are hidden on the way in, as `share` hides them (refused the same way where a replacement already occurs in your text; a form of your project folder first used then gets a marker of its own), and `workspace_read` shows you the files with your real names. What workers of the other group changed, or anyone outside the hub's tools (in an editor or with a program: there is no record of who that was, so it counts as an unknown writer, also when it was you in the folder `workspace(id)` shows), you read, edit, replace or delete only once the user let it through (section 8); until then writing or deleting that name (also in another letter case) is refused: the name is taken by a change waiting for the user's review.

**Working in a workspace (agents).** `workspace(id)` shows the task (as the user let it through the gate, if it held it), the files (sizes, what changed) and the notes. `workspace_read`, `workspace_write`, `workspace_edit` (one exact, unique replacement) and `workspace_delete` change the files; a worker reads them exactly as they are in the workspace. Paths are relative to the workspace: absolute paths, `..`, links, `.git`, Windows short names such as `GIT~1` (on Windows any name with `~` and a digit), a name that differs from an existing one only in letter case, secrets file names and paths over 1000 characters are refused. Several workers (agents and models) can work at once: changes are made one at a time per workspace, and a file is always replaced whole, so no edit that was reported as done is lost, and nobody ever reads half a file. `workspace_note(id, text)` sends a note to everyone working on the workspace (its owner and the other workers), for questions and answers; it is how a worker reaches the owner, never by the owner's name: a worker's message to the owner's session by name is refused (pointing to `workspace_note`), and a name hidden from it is as unknown to it as a name nobody holds. `workspace_done(id, summary)` tells the owner, in its inbox with the list of changed files (a new file by name only if this worker made it; the others are counted; changes that wait for the user's review before the owner may read them are only counted, with no names or line counts), that the work is ready (call it again after more work). A worker that changes the copy in its own editor or with its own programs (the folder is shown for that where it can be) makes changes the hub has no record of: they count as an unknown writer's, so with the gate on the owner reads them only after the user's review; `workspace(id)` says so. `share(files=..., workspace=<id>, ...)` passes a part on, with more names hidden if you like: its changes are applied into the workspace it came from by the agent that passed it on, and the original owner never needs to know. There they count as written by the part's workers and by the agent that passed it on (undoing its replacements turns the workers' words into text it chose), so with the gate on, a part cannot carry one group's text to an owner of the other group unreviewed.

**Models in a workspace** get only its files: `read_file`, `list_files` and `search_files`, plus `write_file`, `edit_file` and `delete_file`, all confined to it. No `git`, no project folder, no `AGENT_HUB_FILE_ROOTS`; `web_search` stays, and `screenshot` opens public web pages only (below). What you send them (the thread, `files=`, which are workspace paths there, the system prompt) has the hidden names and your project folder replaced; what a worker sends its models goes as the worker wrote it. A thread keeps the workspace it started in.

**Getting the work back.** `workspace_diff(id)` shows the changes as a unified diff with your real paths and the hidden names back, as apply would write them, and flags first what to read carefully: files changed on disk since they were shared (conflicts), new or changed files that programs or agents act on by themselves (hidden folders and files such as `.claude/` or `.github/`, build scripts, `AGENTS.md`, `CLAUDE.md`), and spots where a worker wrote a replacement string, which apply turns into what it hides (a name you listed, or for the hub's marker your project folder's path). It starts with a review token. `workspace_apply(id, review=<token>, files=None, delete=False)` writes exactly the changes that diff showed (pass the same `files` as to the diff): if a worker changed the workspace since, or no token is given, nothing is applied and you get the new diff with its token. It writes a changed file only if its original is still as it was when shared (otherwise it is reported as a conflict: apply it by hand from the diff, or share it again), a new file only where nothing exists, a deletion only with `delete=true`. It never writes through a link, into a secrets file, a `.git` folder, the hub's own folder or data, or outside the folder the files came from. A file it changes is replaced whole (written beside it, then renamed over it), keeping its permissions. Applied files become the workspace's new starting point: each is recorded as applied together with its write, so if the hub's database is too busy (another session holds it), that file and the ones after it are reported as not applied and left as they were: apply again in a moment. `workspace_close(id)` deletes the copy (and the parts workers passed on from it) and ends everyone's access. A workspace is deleted, with every part passed on from it, 30 days after the last change, note or share in any of them.

Only the session that shared a workspace can diff, apply or close it, so a session that restarted no longer owns its workspaces. You can always see and apply them yourself: in the dashboard (tab 0) or in a terminal with `uv run agent_hub.py workspace list`, `... workspace diff <id>`, `... workspace apply <id> [--delete]` and `... workspace close <id>` (apply and close ask first; apply writes exactly the diff it printed, and nothing if a worker changed the workspace while you read it).

**Isolated sessions.** `AGENT_HUB_ISOLATED=1` in a worker agent's MCP config makes that session a contractor that sees only what is shared with it. `peers` shows other agents by name and status only (no folders, descriptions or reservations) and models by name only. There is no board and no public message, no `reserve`/`release`, no `review`/`debug`; its models get no project files and no `git` (only a workspace given to it, or no files at all), and `files=` takes only workspace paths. Its `screenshot` opens public web pages only, and it is never shown a workspace's folder on disk. It can still message agents, ask models (questions without files, or in a workspace) and pass part of a workspace on.

**What workers are shown.** Nothing the hub shows a worker names a real path, your project folder or a hidden name: not the message, the workspace tools or their errors (a file system error passes on its reason, never a file name), the notes, the thread or the models' requests (another session's messages and names in a thread reach a worker's models as the worker is shown them, in the history, the speaker labels and the list of participants). What you write into the workspace yourself is hidden on the way in. `peers` shows a session that works on a workspace someone else shared the other agents by name and status only, as for an isolated session (no folders, descriptions or reservations), with your entry under your name as hidden and marked as the one that shared it. Text that came from another session, the user or a provider (messages, posts, notes, names, reasons), as a worker reads it through the hub, has the hidden names of its workspaces replaced too, and so do the names of everyone working on the workspace wherever they are shown (`workspace_note`'s result included). A worker's own words are never rewritten (its arguments, paths it typed, its own messages), and a name hidden from it (your agent name, or any name that holds a hidden one) is exactly as unknown to it as a name nobody holds, so the hub's answers cannot tell it which of its guesses is a hidden name. The workspace's folder on disk is shown to an agent worker (for its own editor and tests) only when its path is not inside your project folder and holds no hidden name; never to an isolated session or to models.

**Screenshots in a workspace.** A model working in a workspace, and an isolated session, can screenshot public web pages only: a page on this machine, a private, link-local or (IPv6) site-local network, or a reserved range (also behind a name, also an IPv6 address that carries such an IPv4 one) is refused before any browser starts. The browser is then pinned to the address that was checked, with no proxy: a redirect, an image, a frame or a script's request to any other host finds nothing, and a name that later points elsewhere (DNS rebinding) cannot lead it back to a local page. In other sessions, screenshots of `localhost` work as before.

**The limits.** This is isolation inside the hub. A live agent with its own shell on the same machine can still browse the disk: for full isolation, run the worker agent in a container, as a separate OS user or on another machine without access to the project, and give it only the hub's tools. The hub's database and the workspaces folder are on the machine the hub runs on, and a worker that can read `hub.db` can read the mapping (real paths, hidden names): that is the limit of hub-level isolation. A name is hidden only where it appears exactly as listed; another spelling, an abbreviation or what the code reveals by itself is not. The workspace folder's path, where it is shown, contains the name of your home folder. What workers write into a workspace passes between the workers (and the models they ask there) like a file on disk, without the gate; only your own view of their changes (and your models') is reviewed (section 8).

## 8. The gate

With the gate on, requests wait until you approve them. You read what would be sent (for a model call: the system prompt, the messages with their attached files, and the model's own reasoning from its earlier answers when that goes back to it), then approve it, deny it (with a reason only the requester sees), or edit it first (web searches, screenshot questions, agent messages, posts and replies). Nothing held at the gate is sent or shown to anyone else before you decide. Every request gets a deadline when it is made, `AGENT_HUB_GATE_TIMEOUT` (10 minutes) later: a request nobody decides on by then is denied (expired), also when the session that asked has crashed, and after its deadline it can no longer be approved. A held message's sender then learns why in its inbox. A model call, web search, screenshot or file read needs its session to carry it out, so it also expires as soon as that session ends; a held message, post, reply or publication does not, and waits for your decision until its deadline.

- `AGENT_HUB_GATE=cross` holds requests that cross between abliterated and standard models or agents, in both directions: an abliterated model's prompt to Claude, Claude's prompt to an abliterated model, an abliterated agent's message to a standard one (and the reply), a web search or screenshot an abliterated model asks a standard one for, a thread with an abliterated agent's text handed to a standard model, and so on. Which group wrote a message is recorded when it is written, so it does not change when that agent leaves; messages from before this was recorded count as both groups (so they are held). A message is checked against the session that actually receives it: if, before it is read, its recipient's name passes to a session of the other group (or to one whose own gate would hold it), it waits at the gate before that session gets it.
- `AGENT_HUB_GATE=all` holds every request.
- **Public messages wait in both modes**, because agents of both groups can read them: other agents read nothing public until you approve its publication. That covers posts, public requests to models or agents, replies to posts, answers to public messages, and a model's answer to a public request (and a public discussion's transcript). The session that wrote or asked for it reads it at once. Where one decision covers both, you are asked once: approving a public request to a model (or an agent) also publishes the request; a model's answer to it, which you have not seen yet, is a second request (kind `publish`); a public discussion's topic is published with its first approved model call, and all its turns at once with one approval of the transcript at the end. If you deny (or let expire) the publication of a model's answer or a transcript, it stays private to the session that asked, and that session is told why (in its inbox, with the answer, in the thread and on its board).
- **Replies are messages too:** an agent's reply to another agent is held like any message between them (`cross`: when it crosses groups; `all`: always), can be edited, and is delivered once approved. Each message gets one reply (a reply you denied does not count), so one approved message does not open a channel back. A model's answer to a private request is not held: the request was the thing to approve.
- **Whose settings count.** Each session applies its own `AGENT_HUB_GATE`, `AGENT_HUB_GATE_KINDS` and `AGENT_HUB_GATE_TIMEOUT`. A message or reply between agents is held when the sender's or the recipient's settings hold it (a joined session records its settings, and an agent message carries its sender's, for the reply); a model call, web search, screenshot, file read or post follows the settings of the session that makes it. So put the gate settings in `keys.env`, which every session reads, not in one client's MCP config. `peers` shows this session's gate and each agent's; `--check` warns when they come from the environment rather than `keys.env`.
- Mark models with `"abliterated": true` in `models.json`, and agent sessions that run an abliterated model with `AGENT_HUB_ABLITERATED=1` in their MCP config.
- **Models outside your models list** (`provider:model-id`, section 5) count as an **unknown group**, both abliterated and standard: when the gate covers `model_call`, a request to one is held for every session, standard or abliterated (as a request to the other group would be), and the gate shows it as "group unknown: not in your models list". The same goes for a web search or a screenshot such a model does, and its answers count as both groups wherever they are read later (a discussion's next turn, a thread handed to another model). Put the model in `models.json` (with `"abliterated"` as it is) to have it treated as its group.
- **Workspaces:** giving a workspace to an agent is an agent message and asking a model to work in one is a model call, held by the same rules (`cross`: when it crosses groups; `all`: always): you read the task and the file list, and the dashboard's Workspaces tab shows the files as shared (`f`), before access is granted or the model is called; if you edit the message, the worker's `workspace()` shows the task as you edited it. A worker's `workspace_done` note and every `workspace_note` (one request for all its readers, editable) are held like messages, and what you approve, edit or deny is what `workspace()` shows (a denied one is shown as such to its writer, with your reason). Every change the hub's tools make in a workspace is recorded with who made it (a session, or the model it asked: its group and gate settings) and the content it leaves, before the change is made, with the workspace's lock held, so nobody reads a change of the hub's tools before its record is in (if the database cannot take the record, the change is refused and nothing changes). A part applied into the workspace it came from is recorded with the part's writers and with the agent that passed it on. A file counts as theirs when it is exactly content one of those changes left (also an earlier one: such content holds nothing but their text); anything else, an edit made in an editor or by a program, counts as made by an unknown writer, of both groups, and a recorded change made on top of such content carries that along (an edit is recorded as made from exactly the bytes it read). The owner reads the changes of a worker of the other group (or of an unknown writer) only through the gate, as it would read that worker's message, decided on exactly the content it reads: its `workspace_diff` waits until you approve exactly the diff it would read (one request, not editable), its `workspace_apply` writes exactly that approved diff, and `workspace_read` of such a file waits for that review. The request and the owner's texts say what the hub knows about who wrote it: the groups of the recorded writers and, where there is one, an unknown writer (changed outside Agent Hub's tools); an editor's edit in a team of one group is never labelled with the other group. If nobody decides a review before its deadline, the owner's next call asks you again. A denial stands for exactly that content: once the changes are different, the owner's next call asks you anew (you can still read and apply it yourself in the dashboard or with `agent_hub.py workspace`). A model the owner asks to work in the workspace counts those writers among the origins of its request, and its file tools withhold what you have not let through for the owner (a file's content and size, search hits in it, a new file's name; it cannot edit, replace or delete it either: writing or deleting that name, also in another letter case, is refused as taken by a change waiting for your review, without saying whose or how it is spelt); the owner cannot attach such a file or pass it on in a part before that (passing on a folder that holds such files is refused, counting them, naming none); its `workspace()` names no such new file and gives no such file's size. Files the hub leaves aside (binary files, links, build folders) are counted, not named, in what the owner and its models read while the gate is on, since workers named them; you see their names in the dashboard and with `agent_hub.py workspace diff`. Between the workers themselves, what they write passes like files on disk, without the gate. A note reaches a session as a message from its writer would: held when the writer's settings (recorded with the note) or the reader's hold it; your approval covers the sessions working on the workspace when the note was written, so one given the workspace later gets an earlier note only if neither gate would hold it (`workspace()` counts the others). Give a workspace to one group only if that matters.
- **The hive** (section 12): a note, decision, stance, task or note on a task of the other group is read only once you approve it (requests of kind `memory`, `decision`, `stance`, `task`, `task_note`), when the writer's or the reader's gate covers `agent_message`; its own group reads it at once.
- `AGENT_HUB_GATE_KINDS` picks what is held: `model_call`, `web_search`, `screenshot`, `agent_message`, `file_read`, `publish` (default: all but `file_read`). Without `publish`, public messages are held only by the rules of their own kind.

Decide in the dashboard (tab 2) or in a terminal with `uv run agent_hub.py gate`. Only you decide: no MCP tool can approve anything, and the models' tools cannot run commands or write files (except in a workspace's copy, which only you or the session that shared it apply). `peers` tells agents how many requests are waiting. As with privacy, an agent with its own shell access could still edit `hub.db` directly.

## 9. Dashboard

```
uv run /absolute/path/hub_tui.py
```

A live terminal view of the hub with ten tabs: overview, approvals (the gate, with the time each request has left; requests past their deadline are listed as expired and cannot be approved), agents, threads (Enter opens the transcript), messages, reservations, models (with 7-day usage), errors, help and workspaces (who shared what from where, with whom, how many files the workers changed; Enter shows the diff with the real paths and names and the notes, `f` the files as the workers got them, `a` applies, `d` applies with deletions, `c` closes, each after a yes; `a` and `d` apply exactly the diff on screen, and in the list they open that diff first; if a worker changed the workspace after it was shown, nothing is applied and the diff is refreshed). Five more tabs for the hive (section 12): `h` its settings (Enter changes the selected one, after a yes; `x` drops your value, also one stored in the settings table that cannot be used), `m` shared memory (Enter shows a note in full, `x` deletes it), `l` the decision log (Enter shows a decision with its stances and what replaces it, `w` withdraws it, `x` deletes it; the confirmation says what that does to the decision it replaced), `t` the task board (Enter shows a task with its history; there `s` sets its status, `a` who it is meant for, `x` deletes it), `s` the model track record's scores (Enter shows a model's ratings with the raters' notes, `x` resets them); `/` on notes, decisions and tasks looks in the whole text. Everything an agent wrote is shown as plain text: markup in a name or a message (styles, click actions) does nothing, also in the notifications. Keys: `1`-`9` and `0` switch tabs (`?` or F1 for help), `h`, `m`, `l`, `t` and `s` the hive's, `/` filters, `k` cycles the message kinds, `r` refreshes, `q` quits. It only reads the database, except for your decisions at the gate, applying or closing workspaces, and the hive (settings, deleting notes, withdrawing or deleting decisions, changing or deleting tasks, resetting ratings). `hub_tui.py --once` prints the overview and exits. Set `AGENT_HUB_TUI_REFRESH` to change the refresh interval (2 seconds). It uses the same `AGENT_HUB_HOME` and `AGENT_HUB_DB` as the server (also from `keys.env`).

## 11. Good to know

- **Cost.** Every `ask` is a paid API call on your key, and thread history is resent each time. High effort levels, `discuss`, `review` with several models, and tool use (every tool round resends the conversation) multiply that.
- **What leaves your machine.** Prompts and attached files go to the provider you ask. Files whose names look like secrets are refused, for example: `.env`, `*.env` (`prod.env`), `.envrc`, `*.pem`, `id_rsa`, `.netrc` and `_netrc`, `.git-credentials` and git's credential store (`git/credentials`), `.pgpass`, `.vault-token`, `auth.json`, `.credentials.json`, gcloud's `application_default_credentials.json`, files named `credentials` or `secrets` (also `.secrets`) unless they are source code or docs (`credentials.csv` is refused; `credentials.py`, `credentials.component.html` and `secrets.md` are sent), these MCP client configs, whose server entries can hold API keys: `mcp.json`, `.mcp.json`, `.claude.json`, `.codex/config.toml`, `opencode.json`, `claude_desktop_config.json`, and anything under `.ssh`, `.gnupg`, `.aws`, `.kube`, `.docker` or a repository's `.git` folder (its config can hold a token in a remote URL). Backup and editor copies of those files are refused too (`.env~`, `auth.json.bak`, `.claude.json.backup`). Templates (`.env.example`, `*.sample`, `*.template`, `*.dist`) and public keys (`*.pub`) are sent, except from a folder that is refused as a whole, such as `.ssh`. System files under `/proc`, `/sys` and `/dev` are always refused. When a file is refused, the agent is told not to copy its values into the prompt instead and that only you can allow such files (`AGENT_HUB_ALLOW_SENSITIVE_FILES=1`). The check goes by file name only and the list is not complete, so look at what you attach.
- **Searches and images.** A web search query goes to the model or search service that runs it. A screenshot or image goes to the model that describes it, scaled down or converted first when it is larger than that provider accepts (Claude: 8000 px and 10 MB; OpenAI: 30,000 patches of 32 px; DeepSeek: 8192 px and 32 MB; Z.ai: 6000 px, 5 MB, PNG or JPEG only; any other provider: the strictest of these).
- **A model's reasoning** goes back only to that model: within one answer's tool rounds as the API requires (Claude's thinking blocks, OpenAI's encrypted reasoning, OpenRouter's `reasoning_details`), and in later turns of a thread as `reasoning_content` for chat-completions models that return it without `reasoning_details` (DeepSeek needs it there with tools; OpenRouter's reasoning is not resent, since it cannot move into the history the hub rebuilds), only with the answers this session got. When another session continues a public thread, earlier answers go without their reasoning; DeepSeek then answers that request without tools, since with tools its API requires the reasoning of every earlier answer (the answer says so).
- **Screenshots** of web pages are taken by a headless browser and saved owner-only in `~/.agent-hub/screenshots` for 7 days. Only `http`/`https` pages can be opened. For a model working in a workspace and for an isolated session, only public pages, with the browser pinned to the checked address and no proxy (section 7): in a network that reaches the internet only through a proxy, those screenshots fail.
- **What stays.** Messages, attached file contents and requests at the gate (what would have been sent, and your decision) are stored unencrypted in `~/.agent-hub/hub.db` (owner-only permissions). Workspaces (their copies and lock files, and in `hub.db` what was shared with the mapping to your paths and names, and who changed which file with a hash of what they left) are kept until closed, or 30 days after the last change, note or share in them or in any part passed on from them. Shared-memory notes are kept for `memory.retention_days` (180 days), decisions and their stances until you delete them, tasks until 30 days after they were done or dropped (open ones until you delete them), ratings of models until you reset them (section 12). Once they are 30 days old (requests at the gate: 30 days after the decision or expiry), the next session that starts deletes them; SQLite's `secure_delete` overwrites the deleted text, and a checkpoint right after the delete normally gets that into `hub.db` at once, even while other sessions have the database open.
- **Trust.** A reply from another model or agent is advice, not an instruction from you. The server tells agents so, but treat cross-agent messages like any other untrusted input.

## 12. Hive features

Optional features that let the agents of a project build on each other's work: **shared memory**, a **decision log**, a **task board** and a **model track record**. Each is off until you turn it on, and each has options. Their tools are always listed; while a feature is off they refuse with "Shared memory (or Decision log, Task board, Model track record) is turned off in this hub's settings; only the user can turn it on (in the dashboard or the control panel)".

**Settings.** Only you change them: in the dashboard's Hive tab (`h`), in the browser control panel (below) or in a terminal. No MCP tool can.

```
uv run agent_hub.py settings                          # every setting, its value and where it comes from
uv run agent_hub.py settings set memory.enabled on    # asks first (it needs a terminal)
uv run agent_hub.py settings reset memory.enabled     # back to the environment, keys.env or the default
```

A value set there is stored in `hub.db` and wins over the environment and `keys.env` (the variable is `AGENT_HUB_` and the setting's name in capitals, `.` as `_`: `AGENT_HUB_MEMORY_ENABLED=1`), which win over the default. A value that is not allowed is refused there; in the environment it is ignored with a warning (the default applies). Every session uses a change at its next tool call, without a restart. `peers` and `--check` list each setting with its value and where it comes from.

| Setting | Default (allowed) | Meaning |
| --- | --- | --- |
| `memory.enabled` | off | Shared memory: `remember`, `recall`, `forget`. |
| `memory.hub_scope` | off | Also allow notes with scope `hub`, which agents in every project read. |
| `memory.max_entries` | 1000 (10-100,000) | The most notes one project (or the hub scope) holds; `remember` refuses more. Counted for the writer's gate group: the other group's notes that wait at the gate or that you denied do not count for it. |
| `memory.max_chars` | 2000 (100-20,000) | The longest note. |
| `memory.retention_days` | 180 (1-3650) | Older notes are no longer recalled, and are deleted when a session starts. |
| `memory.auto_context` | off | Auto-context with notes (below). |
| `decisions.enabled` | off | The decision log: `decide`, `decisions`, `weigh_in`. |
| `decisions.auto_context` | off | Auto-context with active decisions. |
| `context.max_items` | 5 (1-30) | Auto-context: the most notes and decisions in one request. |
| `context.max_chars` | 4000 (200-40,000) | Auto-context: the most characters of them in one request. |
| `tasks.enabled` | off | The task board: `task_add`, `tasks`, `task_claim`, `task_update`. |
| `tasks.claim_minutes` | 60 (5-10,080) | The claim timeout: a claim with no news from its agent for this long returns to open. |
| `tasks.max_open` | 200 (10-10,000) | The most unfinished tasks one project holds; `task_add` refuses more. Counted for the writer's gate group, as `memory.max_entries`. |
| `track.enabled` | off | The model track record: `rate`, `models_ranking`. |
| `track.auto_route` | off | Auto-route: `to="best"` picks the best-rated model (below). |
| `track.min_ratings` | 5 (1-1000) | Auto-route: the fewest ratings a model needs for a kind of request to be picked. |

**Shared memory.** `remember(text, tags, scope)` saves a note for the other agents working on the project: a convention, a gotcha, a fix that worked, a fact about the environment. A project is the git repository's top folder (the same from any folder in it), else the session's working folder; with `memory.hub_scope` on, `scope="hub"` notes reach every project. `recall(query, tags, limit)` finds notes, the best match first (SQLite's FTS5 full-text search; where Python's SQLite lacks FTS5, a plain word match), each with its id, author, age and tags; an empty query lists the newest. `forget(id)` deletes a note, only for the session that saved it; you can delete any in the dashboard (`m`, then `x`) or the control panel.

**Decision log.** `decide(title, decision, why, alternatives, supersedes)` records a decision for the project; `supersedes=<id>` replaces an active one. A decision is superseded while a later one in force (not withdrawn) replaces it, directly or through decisions that replace it in turn, and only for the agents that can read that later one (see The gate, below). So a withdrawn replacement no longer replaces anything, and if you delete a decision in the middle of a chain (A replaced by B, B by C), the ones after it replace the ones before it (C replaces A); delete the last one and the one it replaced is in force again. `decisions(query, status, limit)` lists them (`active` by default, or `superseded`, `withdrawn`, `all`) with their reasons, alternatives, author, date, what superseded what, and the stances. `weigh_in(id, stance, note)` gives this session's stance on an active decision, `agree`, `disagree` or `question`, with a note; calling it again replaces it. The session that recorded a decision withdraws it with `weigh_in(stance="withdraw", note=why)`; you can withdraw or delete any in the dashboard (`l`) or the control panel. Decisions are kept until you delete them.

**Task board.** `task_add(title, details, depends_on, assignee)` adds a task to the project's board (the same project as for notes): `depends_on` lists tasks that must be done (or dropped) first, `assignee` the agent name it is meant for. `tasks(status, mine, limit, id)` lists the unfinished ones by default (or one status, or `all`), oldest first, each with who added it, who claims it, what it waits for and its latest notes; `mine=true` only yours (added, claimed or meant for your name); `id` one task with its whole history. `task_claim(id)` claims an open task, after `join`: one session at a time, not while it waits for unfinished tasks (the refusal names them), and not a task meant for another agent that is in the hub now. `task_update(id, status, note, assignee)` reports on a task: statuses are `open`, `claimed`, `in_progress`, `blocked`, `done` and `dropped`; only the agent that claims a task or the one that added it changes its status or who it is meant for (`claimed` and `in_progress` need the claim: `task_claim` first; `open` gives a claim back), and any agent of the project adds notes. The history records who changed what and when, with each note. A claim lasts while its session is in the hub and sends news (`task_claim` again or any `task_update` renews it): when that session has ended, or after `tasks.claim_minutes` without news, the task is open again the next time an agent looks (its history says why). An agent's `inbox` mentions open tasks meant for its name once; when a task is done, the answer names the tasks that can be claimed now. In the dashboard (`t`) or the control panel you change any task's status (`open` or `blocked` drop the claim; `done`, `dropped`; in the control panel with a note of yours) or who it is meant for, with your change in its history, or delete it (tasks that waited for it no longer do). Done and dropped tasks are deleted 30 days later; open ones stay until you delete them.

**Model track record.** After an agent has checked a model's answer, `rate(message_id, verdict, note)` records `useful`, `partly` or `wrong` for that model and that kind of request: `ask`, `ask_many`, `discuss` (each turn on its own: its id is in the transcript's headers), `review`, `debug`, `web_search` and `screenshot` (for these two, the model or search service that did it). `message_id` is the request's id (or the answer's). Only the session that received an answer rates it, once (rating it again replaces it); agents' answers and failed requests are not rated. While the track record is on, an answer from a model ends with how to rate it. `models_ranking(category)` shows each model's score per kind of request (useful 1, partly 0.5, wrong 0, averaged) with the counts, the best first; `peers` shows the three best per kind. The scores are hub-wide (a model is the same in every project). A rating's note is for you: the dashboard (`s`) shows the ratings with their notes, the control panel the latest ones; agents see only the counts. You reset a model's ratings for a kind of request in either (`x` in the dashboard), or all of them in the control panel.

**Auto-route.** With `track.auto_route` on, `to="best"` in `ask`, an entry `"best"` in `ask_many` (each one adds the best-rated model not listed yet) and `review` / `debug` without `models` pick the ready model with the best score for that kind of request among the models in your models list (the built-in ones and `models.json`) with at least `track.min_ratings` ratings (on a tie, the one with more ratings). Ratings of a model reached as `provider:model-id` are kept and shown, marked "not in your models list: auto-route passes it over", but never route a request: one agent cannot send the others' prompts to a model you never set up. If no model has enough ratings, the default answers: for `review` and `debug` their usual default, all of it (`AGENT_HUB_REVIEW_MODELS` / `AGENT_HUB_DEBUG_MODELS`, else the first ready of `opus-5.5`, `sol-6.1`, `fable-5.2`, ...), each answer saying so; for `ask` and `ask_many` the first ready of that order. The answer says which model was picked and why (its score and counts, and the runner-up). With more `"best"` entries than ready models, `ask_many` picks each ready model once and says how many entries were left out. While auto-route is off, `to="best"` is refused and `review` and `debug` choose as before. `best` cannot be an agent's name.

**Auto-context.** With `memory.auto_context` and/or `decisions.auto_context` on, `ask`, `ask_many`, `discuss`, `review` and `debug` send a model the notes (and active decisions) most relevant to the request, found by its words (the prompt, a discussion's topic, a review's focus and file names, a debug's problem and error), at most `context.max_items` within `context.max_chars`. They go before the prompt in a `<hive-notes>` block that says they are other agents' notes, not the user's instructions (never in the system prompt), and the answer's footer says how many went with it. They are not kept in the thread: a later request gets the notes for it. Not for public requests (every agent reads their answers), not in a workspace (nothing may tie its model to a project), and not in sessions without a hive.

**The gate.** Notes, decisions, stances, tasks and the notes on tasks record their writer's gate group. When the writer's gate or the reader's covers `agent_message` (`cross` or `all`), a row of the other group (abliterated or standard) is read only once you approve it at the gate: the writer's gate asks you when it is written, a reader's gate when that reader looks for it with `recall`, `decisions` or `tasks` (at most 10 requests per call). There is one request per item, however many agents look for it at once. You can edit a note, a stance's text or a note on a task before approving it; a decision or a task is approve or deny. A task's status changes, claims and the hub's own entries in its history hold no agent's words and are seen at once; a note of the other group shows there as waiting for your review. Approval lets every agent of that group read it. A denial stands for as long as the item exists, for every agent of that group (also one whose own gate is off), and you are not asked about it again; it is recorded on the item, so it outlives the request (decided requests are deleted after 30 days); the writer is told why. Rows of the reader's own group are read at once, also with `all`. A decision that replaces one of the other group supersedes it for that group only once they can read it: while it waits for you (or after you denied it), they see the earlier decision as active, with a hint that a newer one waits for your review, and their models keep getting it. A model call with auto-context counts the notes' writers among its origins, as it does a thread's.

**Isolation.** Isolated sessions and sessions working on another session's workspace have no shared memory, decision log or task board: those tools refuse with a neutral text (they would tie their piece to a project), `peers` says so, their model requests carry no notes, and their inbox mentions no tasks. The model track record holds no project's text, so they rate the answers they get and read the scores like any session.

**Control panel.** The same settings, notes, decisions, tasks and model scores in your browser:

```
uv run /absolute/path/hub_web.py              # prints a sign-in link; --port N (default 8777, 0: any free port)
```

Open the printed link: it works once and signs that browser in (restart `hub_web.py` for a new one; Sign out ends it). Pages: an overview (agents online, how many requests wait at the gate, each feature's state), settings (every hive setting with its value and where it comes from, as this process sees the environment and `keys.env`; validated like `agent_hub.py settings`), memory (search the whole text, delete), decisions (search, filter by status, withdraw with a reason, delete), tasks (every project's tasks with who added them, for whom, the claim, what they wait for and their latest history; search the whole text, notes included, filter by status; set a status with a note of yours, assign, delete) and model scores (per kind of request and model, with the counts and the raters' latest notes; filter by kind; reset a model's ratings for a kind, or all). Every change asks for a confirmation and goes through agent_hub's own code; pages read `hub.db` read-only and work before it exists (a setting you change creates it, as `agent_hub.py settings set` does). Approvals stay in the dashboard and `agent_hub.py gate`. Security: it listens on 127.0.0.1 only; the link's token becomes an HttpOnly, SameSite=Strict cookie that every request needs; a Host other than `127.0.0.1:<port>` or `localhost:<port>` is refused (DNS rebinding); changes are POST forms with a CSRF token and a matching Origin, requests another site starts are refused, and there are no CORS headers; there is no JavaScript (a strict Content-Security-Policy), and everything agents wrote is shown as plain text. As everywhere, a program running as you can read `hub.db` without the panel.

**Limits, honestly.** Notes, decisions and tasks are other agents' words: tools and models get them labelled as such, never as your instructions, but they can still be wrong or written to mislead; agents should check them. Ratings are agents' opinions, from both gate groups: an agent that asks a lot can move a model's score (only answers it received count, one rating each), and auto-route then follows it, but only among the models in your models list; the gate still holds whatever request that leads to. A claim is advisory, like a reservation: nothing stops an agent from working on a task another claims. Memory is shared by design within its scope: every agent of the project reads it (and of every project, for hub-wide notes). Text that looks like a secret is refused (private keys, common API key and token formats, `NAME=value` or `name: value` where the name says it holds a secret and the value looks like one, also after a label such as `Staging: DB_PASSWORD=...`, a password in a URL such as `postgres://user:password@host`, the credentials of an `Authorization:` header or a `Bearer` token, and the keys this server knows; placeholders such as `$TOKEN`, `${TOKEN}` or `<password>` are fine), but that is a heuristic: it cannot recognise every secret (a password in plain prose, for example). As everywhere in the hub, an agent with shell access can read or change `hub.db` directly.

## 13. Fleet mode: a hub on a VPS or website, with a director (2.0)

A **fleet server** (`hub_server.py`) runs on a VPS or behind a website. People's agents join it over the internet, report in and wait for orders from the **director**, the one member who leads the fleet: a human working through their AI agent, who can always step in through the web panel. The director (and the **trusted partners** it marks) hand out **orders**: **workspace tasks** (files the director shares from its project, with neutral paths and the names it hides, as `share` does) and **repo tasks** (a repository the worker's agent clones). Workers claim them, work in a task folder of their own, report back, and the director reviews and accepts or rejects the result. The director role can be **handed over** to a trusted partner.

**Roles.** The **owner** runs the server (commands on the VPS, or the panel through an owner link), picks the director ("the website/VPS decides the director") and can replace it at any time. The **director** (exactly one) gives orders, reviews results, admits, rejects, removes and bans members, makes invites, changes the join settings, pauses the fleet, writes to members or to everyone, marks trusted partners and hands its role over. **Trusted partners** help with the lobby, invites and settings, give orders of their own (and decide their results) and can receive the director role. **Workers** claim orders and write to the director. Members **in the lobby** wait for approval. **Banned** keys never get in again.

**Identities.** Each computer makes an Ed25519 key per fleet (`~/.agent-hub/fleet/<server id>/key`, owner-only; never shown to models or attached: the hub treats the whole `fleet` folder as its own private data; the order task folders are elsewhere, below). Its **fingerprint** (`7841:7f47:...`, 8 groups) and a **word phrase** derived from it (`silver lantern parrot carrot canoe jelly`) are the identity shown everywhere: compare them over another channel, for example on a call, before you trust someone (`agent_hub.py fleet identity` shows yours). A member is one key: only the key's canonical base64 is accepted, so a banned key cannot come back written another way.

**The server's own key, pinned.** Every fleet server has an Ed25519 key too (`server.key` in its home; `hub_server.py owner key` shows its fingerprint and phrase; invite links carry the fingerprint after `#key=`). The first `fleet_join` **pins** it on this computer, with the address it joined at (trust on first use; or give the whole fingerprint you got from the owner or the director: `fleet_join(..., server_key=...)`, or use an invite link; the six-word phrase is for comparing by voice and is never accepted as a pin). From then on this computer refuses, with a WARNING, any other key for that fleet, and any other address unless the pinned key proves it (a server that really moved signs a challenge naming its new address, which the client checks with the pinned key; then the new address is saved). **Re-pinning is your decision, not your agent's**: no agent tool replaces or removes a pinned key or a saved address. `server_key=` and an invite link's `#key=` only set the expected key of a first join; for a pinned fleet they change nothing (one that differs from the pin is refused), and the refusals never print the key the server offered (so an agent cannot copy it back). If the owner really replaced the key, or moved the fleet to a new address with a new key, you run **`agent_hub.py fleet pin [server] [--url NEW]`** in a terminal: it shows the new key's fingerprint and phrase next to the one pinned before (and the address change), checks that the server holds that key at that address, and asks you. `agent_hub.py fleet list` shows each fleet's pinned fingerprint, or that it has none. Commands that take a fleet (`--server S`, `fleet identity S`, ...) accept its server id, address or name; a name that two joined fleets share (a server can call itself anything) is refused with both listed (id, address, server key), and you give the id; an agent's `server=` works the same way. A computer that joined a 2.0.0 server before servers had keys is not reconnected to it and is told so: you run `agent_hub.py fleet pin` (or give your agent the fingerprint the owner printed with `owner key`, for `fleet_join(server=<its saved address>, server_key=<fingerprint>)`; only at the saved address).

**Logging in, and what a signature binds.** The server gives a one-time challenge for the member's key, the purpose and the exact origin (`scheme://host[:port]`) the member connects to, **signed with the server's key**; the client checks that signature with the pinned key, and that it names the address it connects to, before it signs anything. The member's signature then covers the purpose (and what the action is about), the server's id, **the fingerprint of the server's key, the exact origin**, the challenge, the time and the member's key; the server accepts it only for its own key and its own public origin. So a signature made for one server is useless at any other, and a server at another address that relays a member's login to the real one gets nothing it can use (the real server refuses a signature naming the relay's address, and the client refuses a challenge naming another address). A signature cannot be replayed (the challenge is used up, the time must be within 5 minutes). A challenge lives 30 seconds, and nobody can block other members' logins by asking for many: one address (an IPv6 /64) holds at most 10 outstanding challenges (a new one replaces its oldest), and when the server's store of them is full, the address holding the most loses its oldest; a login is never refused because the store is full. The access token is short-lived (15 minutes; the client logs in again by itself), stored on the server only as a hash, and revocable. After any lost or failed connection (a server restart, a fail-over, a broken kept-alive connection) the client keeps its token but sends **no request carrying it** (not the long-poll, not a heartbeat, not a GET tried again) until the server **proved its key**: it signs a fresh random nonce of the client for the client's origin, checked with the pinned key (a server that came back with another key, or another server that took over the address, is noticed then, and gets no token); a proof counts only if no connection of the client was lost since it began. While no connection is lost, requests on new connections (the heartbeat opens one every few seconds) rely on TLS, as before. This proof costs no login, so after a restart every member reconnects at once, also many behind one address; a login is charged to the address's rate limit once, at its challenge, and a 429 is retried after the server's Retry-After plus a random part. The client takes Retry-After only as RFC 9110 defines it (whole seconds, or an HTTP-date in any of its three formats: IMF-fixdate, and the obsolete RFC 850 and asctime forms), at least 1 and at most 300 seconds; anything else (a negative or fractional number, NaN) is ignored and the normal backoff applies. Every request is checked **on the server** for the identity behind its token: a worker that calls a director endpoint directly is refused, whatever its client does. Some actions need more than the token: marking a trusted partner, offering and accepting a handover, and approving or refusing orders from the command line are each **signed with the member's key for exactly that action** (the purpose and what it is about: the other member's fingerprint, the handover and the director, or the orders with the digest of their content), with the same binding to the server's key and origin, so a stolen token, or a signature for something else or for another server, cannot do them.

**Joining.** The join mode is `open` (anyone with the address), `invite` (an invite link: one or more uses, an expiry, revocable; the default) or `closed`; **approval** on (the default) puts new identities in the lobby until the director or a trusted partner admits them, with the name, description, agent/model and human contact they gave; off admits them at once. Both change live, from the agent tools, the panel or the owner's command line, and apply to the next join at once; members keep their role. In open mode one address may make only so many new identities per hour (`new_keys_per_hour`, 5).

**For the agents (client side).** Fleet mode is off until you turn it on: set `AGENT_HUB_FLEET=1` in `keys.env` (every session) or in one agent's MCP config (only that agent). Without it the fleet tools are not listed and nothing changes. Once this computer has joined a fleet, fleet mode stays on by itself (`AGENT_HUB_FLEET=0` turns it off), and every new session **reconnects by itself** to the fleets this computer joined and did not leave (`AGENT_HUB_FLEET_CONNECT=0` turns that off, or lists the server ids, names or addresses to reconnect to); `fleet_status` shows them, also the ones it could not reconnect and why. Then tell your agent the server's address or give it the invite link.

One session at a time uses a computer's identity on a server (a second session is refused; a second identity needs another `AGENT_HUB_HOME`). A session may be in several fleets; `server=` picks one when it is.

**Orders.** An order has a title, instructions, a kind (`workspace` or `repo`), who it is for (`to`: one member, several members, the first of whom to claim it takes it, or omitted: anyone in the fleet, the first to claim it; `each=true` with several members makes one order for each of them), a priority (`low`, `normal`, `high`, `urgent`), an optional deadline and acceptance criteria. Its status is one of: **waiting for approval** (dispatch approval, below), **queued** (for anyone) or **offered** (to named members), **claimed**, **in progress** (its files fetched, or progress reported), **reported** (waiting for review), **accepted**, **rejected**, **cancelled** or **expired**. A claim goes back up for claiming (**re-queued**, its claimer told) when it gets no news for the order's claim time (`claim_minutes`, 60 by default: claiming, fetching the files, progress and questions are news; the worker's agent is told the time when it claims, renews it with `fleet_progress`, and is warned before it lapses; a report after a lapse says the claim ended and why), when its claimer has been offline for `requeue_offline_seconds` (300), or when it leaves, is removed, banned, or becomes the director. The time a server is down never counts: offline time and the claim time are measured from its start at the earliest, and for `--start-grace` seconds after a start (90) no claim goes back up while members reconnect. A worker that declines an offer or gives back a claim is not offered that order again unless the director names it again; when one member takes an order, the others it was offered to are told. An order that is not reported by its deadline **expires**. Every step is in the order's history and reaches whom it concerns at once: the offer reaches a waiting worker in well under a second.

**Workspace tasks.** `fleet_order(kind="workspace", files=[...], replace={"AcmeCorp": "Company"})` makes a workspace on the director's computer exactly as `share` does (section 7: paths relative to the files' common folder, your project folder never shown, the names you list hidden in contents, file names, the title, the instructions and the criteria; secrets files never copied) and uploads its files, as the workers will see them, to the server (text that looks like a secret is refused on both sides). A worker's `fleet_claim` downloads them into **its own task folder**, `~/.agent-hub/fleet-tasks/<server id>/<order>/` (apart from `~/.agent-hub/fleet`, where the keys are; folders of 2.0.0 are moved there once), and nowhere else (the paths are checked again on the worker's side: relative, no `..`, no links on the way, no secrets files). The worker's agent works there with its own tools. `fleet_report` compares the folder with what was downloaded and uploads **only what changed** (changed, new and deleted text files; binary and very large files and build or cache folders are left aside and named), and refuses while the folder holds a link (symbolic or hard), a secrets file (by name) or text that looks like a secret; nothing outside the task folder is ever read. The director's `fleet_review` puts the worker's changes into the order's local workspace and shows them **with the real paths and names back**, exactly as they will be written, with the review token; `fleet_accept(order, review_token)` accepts the result and writes exactly that into the project, as `workspace_apply` does: a file that changed on disk since it was shared is refused (a conflict: apply it by hand from the diff), new files only where nothing exists, deletions only with `delete=true`. The user can also apply it from the dashboard or with `agent_hub.py workspace apply <workspace>` (the review names it), or with `agent_hub.py fleet apply <order>`. Results of an order made on another computer (a partner's) are shown with neutral paths and applied on the computer that made it. The order's local workspace follows the workspace rules (section 7): it is kept until 30 days after its last change; after that a result is shown with neutral paths only.

**Repo tasks.** `fleet_order(kind="repo", repo_url=..., repo_ref=...)`: the URL must be `https://`, `ssh://` or `git@host:path` (plain `http://` only for 127.0.0.1 or localhost), never a local path, `file://`, `ext::`, an option or credentials; the branch, tag or commit is checked too. Both the server and the worker's client check it. `fleet_claim` gives the worker an empty task folder and the command to clone into it (`git clone --branch <ref> -- <url> <task folder>/repo`): **the worker's agent clones it itself; the client never runs git or anything else**. The report carries a patch file the agent wrote inside the task folder (for example `git -C repo diff > changes.patch`; up to `max_report_bytes`, refused when it looks like it holds a secret) or a pull-request URL (https). `fleet_review` shows the patch and saves it to `~/.agent-hub/fleet/<server id>/results/` for `git apply --check`; accepting decides the order; you apply the patch or merge the pull request yourself.

**Human intervention.** The director's human (and the owner) can always step in, in the panel or on the command line:
- **pause / resume** the fleet: no new orders are offered or claimed while paused, and members are told to wait;
- **dispatch approval** (`dispatch_approval`, off by default): every new order waits until a human approves it, in the panel's Approvals page or with `agent_hub.py fleet approve <order>|all [--no]` on a lead's computer (it shows **all** of each order, a screen at a time, with its line count and content hash, asks in a terminal, and signs the approval with the key for exactly those orders **and the digest of their content as shown**; if you stop reading before the end, nothing is approved). An approval is for that content: a change afterwards (title, instructions, criteria, who it is for) voids it, and the order waits for a human again (a claimer is released and told). The panel's "Approve these" approves exactly the orders on the page as shown. The director's and the owner's humans decide every order; a trusted partner's human only orders made by partners. A leads' agent with its access token alone cannot approve, nor switch the setting: only the panel and the owner do; refusing cancels the order;
- **cancel, edit, reassign** orders; **accept or reject** results (each asks for a confirmation in the panel);
- **take over**: in the panel's Settings, the director's human (or the owner) takes the lead from the agents: while it is on, the leads' agents cannot give, change or decide orders, admit or remove members or change settings with their access tokens (they are told; such calls get HTTP 423), and the humans act in the panel; "Hand back" ends it;
- **kick, ban**, and the owner can always set the director (`owner director`, or the panel's Partners page).

Honestly: these separate the human from the agent's access token, not from an agent that can run commands as you on the same computer. Such an agent could run `agent_hub.py fleet approve`, `fleet confirm`, `fleet pin` or `fleet panel-login` itself in a pseudo-terminal (they use the same key and files; they refuse a plain pipe, not a determined agent). Likewise `fleet_trust` and `fleet_handover` take the fingerprint "your user compared": the client checks it is that member's, but an agent could pass one it read from `fleet_members`; that step is your agent's word. If you rely on dispatch approval, the takeover, trust marks or the runner's confirmations, give the lead's or worker's agent no shell (or run it as another OS user), and keep the panel link to yourself.

**Trusted partners and handover.** The director marks a worker as a trusted partner with `fleet_trust(member, fingerprint=...)`, passing the member's whole fingerprint or its six-word phrase **as its human compared it with the member's human over another channel**; the client refuses if it is not that member's, and signs "trust <the member's fingerprint>" with the director's key (the panel cannot mark partners, except for the owner; the owner can also use `owner trust`). `fleet_trust(member, revoke=true)` takes it back. `fleet_handover(member, fingerprint=...)` offers the director role to a trusted partner (signed for that partner; refused for anyone else); the partner is told, with the director's fingerprint and phrase, and accepts with `fleet_accept_handover(handover)`, signed with **its own** key for that handover and the offering director (only the partner it was offered to can; it may decline). Then the partner is the director and the old director a trusted partner, and **every member is told the new director's name and fingerprint**. With `handover_needs_owner` on, an accepted handover also waits for the owner (`owner handovers --confirm <id>`, or the panel). An offer expires after 24 hours; the director, the partner or the owner can cancel it. Both signatures are kept with the handover, and everything is in the audit log.

**Staying reachable ("keep pinging constantly"), honestly.** An MCP server cannot make a model call tools by itself. What the hub does: a background connection per fleet keeps the session in sync all the time (a long-poll that the server answers the moment there is news, and a heartbeat every 5 seconds, with presence online / working / idle shown to the director; reconnection with jittered backoff when the server or the network goes away, then it catches up on what it missed); events wait in a local queue; `fleet_wait` returns at once when something is queued; every answer ends with the next call for what arrived (claim or decline an offer, review a report, answer a question, stop working on a cancelled order, ...), and the instructions tell joined agents to stay in that loop between tasks. For an always-on worker, the **worker runner** keeps a headless agent in that loop (below).

**The worker runner.** `agent_hub.py fleet run --agent claude|codex|cmd [--command "..."] [--server S] [--pass-env NAME] [--codex-install DIR] [--dry-run]` keeps a headless agent session running in the fleet's task area (`~/.agent-hub/fleet-tasks/<server id>/`, apart from the keys in `~/.agent-hub/fleet`), with this hub as an MCP server, reconnected to that fleet, and a standing prompt to loop on `fleet_wait`, work only in the task folders, renew its claims with `fleet_progress`, and decline what you would not want; when the agent exits, the runner starts it again (pausing longer when it exits quickly, and stopping after ten quick exits in a row). Safety defaults:
- **Locked to its fleet.** The agent's session (the hub started with `AGENT_HUB_FLEET_RUNNER`) works for the runner's fleet only, whatever the agent is asked: it connects only that fleet, every fleet tool refuses another one, and `fleet_join` and `fleet_leave` are refused (they are not among the tools the agent may use either).
- **No permission bypass, ever.** The runner never passes a flag that skips an agent's permission checks or sandbox, and refuses to start when the command or the policy names one (`--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `bypassPermissions`, `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `danger-full-access`). It passes only flags the installed agent lists in its own `--help`, and refuses to start when one it needs is missing.

Do not use it on a computer with data you care about.
  - **The agent's environment** (every agent): the runner starts it with its own environment **without secrets**, withheld by name and by value. Nothing `keys.env` holds ever reaches the worker (not even a provider key the hub uses): no variable whose value is, or contains, a value of `keys.env` or a provider key the hub knows (of 8 characters or more), whatever its name. By name: no variable named like a key, token, secret, password or passphrase (also `APIKEY`, `*_ACCESSKEY`, `*_PW`, `SSHPASS`, `TF_TOKEN_<host>` and camelCase names such as `signingKey`), a JWT, a webhook, a cookie, or authentication and authorization (`NPM_AUTH`, `AUTH_TOKEN`, `AUTHORIZATION`, `XAUTHORITY`; the git identity `GIT_AUTHOR_*` and `GIT_COMMITTER_*` is kept), no password manager's session (`BW_*`, `OP_*`), no cloud, CI and database credentials (`AWS_*`, `AZURE_*`, `GOOGLE_*`, `PG*`, `DATABASE_URL`, ...), and not the ssh or gpg agent. By value, whatever the name: no variable whose value looks like a secret (a key or token in a known format such as `sk-...`, `ghp_...`, `github_pat_...`, `xox...`, `AKIA...`, a private key block, a JWT, a URL with a password, an `Authorization` header's credentials, or a value that contains one the hub knows as a secret). The dry run and the log list every name withheld, and which of them for their values; never a value. A credential under a name and in a format none of these rules know still passes: keep such secrets out of the runner's environment (start it from a clean shell, or as a separate OS user). `--pass-env NAME` passes a variable of the runner's own environment on purpose (never a value from `keys.env`); a name that is not set there is reported with a WARNING at the start (and in the dry run), not passed silently.
  - **The agent's login**: the runner says at the start which login variables it passes to the agent and which it withheld. Claude Code picks its login in its own order: cloud providers when its settings enable them, then `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` in its environment, an `apiKeyHelper` of its settings, `CLAUDE_CODE_OAUTH_TOKEN` (the long-lived subscription login from `claude setup-token`, the usual one for an always-on worker without a browser), then the credentials of `/login` (your subscription or Console account). The environment variables among these reach it only with `--pass-env` (e.g. `--pass-env CLAUDE_CODE_OAUTH_TOKEN`); the runner does not change Claude Code's settings, so an `apiKeyHelper` or an `env` block in its `settings.json` still selects what it says. So: for your subscription, log in with `/login` once or pass `CLAUDE_CODE_OAUTH_TOKEN`; to bill an API key, pass `ANTHROPIC_API_KEY` set in the runner's own environment (not in `keys.env`), or set it up in Claude Code's settings. Codex uses the login it saved (`codex login`: ChatGPT, an API key with `--with-api-key`, or an access token with `--with-access-token`); from the environment, `CODEX_API_KEY` or `CODEX_ACCESS_TOKEN` (a ChatGPT Business/Enterprise access token) only with `--pass-env` (its commands still never see it; `OPENAI_API_KEY` is not Codex's login variable).
  - **The git identity**: when none of `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL` is set in the runner's environment, the agent (and, under Codex, its commands) gets one made from the member's fleet name, `<name> (Agent Hub fleet)` `<name>@agent-hub.invalid` (a non-routable address), so a commit in a repo order works; set the four variables to use your own. The runner's note says which it uses.
  - **`--agent cmd --command "..."`** runs your own command (`{mcp_config}`, `{prompt_file}` and `{task_area}` are filled in): it enforces whatever your command does.
- **A local policy file**, `~/.agent-hub/fleet/<server id>/policy.json` (made on the first run; `agent_hub.py fleet policy` shows it; only you edit it): `accept_types` (`["workspace"]` by default: repo tasks need a shell for git), `max_concurrent` (1) and `confirm_each_order` (on): **you confirm every order** before the agent may claim it, on the runner's terminal or with `agent_hub.py fleet confirm <order> [--no] [--server S]` in another terminal (it needs a terminal). Both show **all** of the order with every field whole (who it is for, the whole repository URL and ref, every file, all of the instructions and criteria: the agent never gets more), wrapped to 76 columns (wide characters such as CJK count two; nothing is cut), with its line count and content hash; `fleet confirm` (and `fleet approve`) page it one screen at a time, counted in your terminal's rows, and confirm nothing if you stop reading before the end. On the runner's terminal (the order's lines are printed there without the time stamps) you answer `y` or `n` (`<order> y` when several wait); an order taller than the terminal (counted in its rows, at most 40) is accepted only with `<order> y <the first 8 characters of its hash>` (it is also written to `runner/order-<id>.txt`); a hash typed with an answer must be that of the order as shown now, or the answer does not count (also for a short order). Typed-ahead input is discarded before every question, and an answer counts only for the version of the order that was on the screen when you typed it (not one shown less than a second before). Your confirmation is for the order **as you read it**: if the director changes it afterwards, before or after the claim, the agent is not let on with it (it is told to stop) until you confirm the changed order ("CHANGED since you confirmed it"). The policy is enforced by the hub in the agent's session (in `fleet_claim` and `fleet_get`), not only by the runner around it.
- **A visible log**: everything the runner and the agent do is printed and kept in `~/.agent-hub/fleet/<server id>/runner/runner.log` (owner-only).
- **An instant stop**: Ctrl-C, or `agent_hub.py fleet stop` from another terminal, stops the runner and the agent's whole process group at once.

The risk, plainly: an always-on worker runs an AI agent on **your** computer on requests from people you may not know. What keeps it in its task area is the agent's own sandbox, as listed above (for Claude Code its permission checks; for Codex its permission profile; nothing for your own command), plus the hub refusing other fleets and asking you about each order. Read the orders you confirm and the log, give the agent no more tools than the work needs, and for real isolation run it as a separate OS user, in a container or on a machine without your data.

**Worker safety.** Everything from a fleet (orders, messages, answers, names, descriptions, the server's own texts) reaches the agent labelled as coming from that fleet, indented, without escape or control characters, as requests from other people's agents, never as instructions that override yours; every order says so. The client never runs anything it receives, never uploads anything outside an order's task folder, never secrets files or the hub's own data, and refuses text that looks like a secret. Your agent (and you) can decline or give back any order and leave at any time.

```
python hub_server.py owner panel-login [--url U]   |   owner panel-logout   |   owner audit [--last N]
```

A member is named by `#id`, name or fingerprint (8+ hex digits). Every role change, admission, rejection, removal, ban, invite, order, edit, reassignment, cancellation, dispatch decision, result decision, trust mark, handover, setting change, token revocation and panel sign-in is in the **audit log** (who, when, what, and the address for the owner).

**The director's panel** (`https://hub.example.com/panel`): **members** (presence, role, current task, fingerprint and phrase, what they say about themselves; remove, ban, lift bans), **lobby** (admit, reject, ban), **orders** (the board by status, each order's details: instructions, criteria, files as the workers see them, questions, reports and its whole history; cancel, edit, reassign), **approvals** (orders waiting for dispatch approval, with their instructions, criteria and files: approve, refuse, or approve exactly the ones on the page; each decision is for the content shown), **results** (each reported result with the worker's summary and its changes: a diff of the workspace files as the workers saw them, or the patch and the pull-request URL; accept, or reject with a reason and what happens next), **questions** (answer them), **partners** (trusted partners with fingerprints and phrases, open handovers; take trust back; the owner marks partners, confirms handovers and sets the director), **invites**, **settings** (join mode, approval, pause, dispatch approval, claim and offline times; take over / hand back), **messages** and the **audit log**. Kicking, banning, rejecting, cancelling, refusing, accepting or rejecting a result, trust changes, handover confirmations and cancellations and setting the director each ask on a page of their own first. Sign in with a one-time link: the director (or a partner) runs `agent_hub.py fleet panel-login` on their own computer (it signs a challenge with their key; the panel is for the director and trusted partners only), the owner runs `hub_server.py owner panel-login` on the server. The link is valid 5 minutes and once (opening it asks before it signs in, so link previews cannot use it up); it becomes a Secure, HttpOnly, SameSite=Strict cookie (8 hours, or until Sign out; `owner panel-logout` signs every browser out). Changes are POST forms with a CSRF token and a matching Origin (requests another site starts are refused), the Host must be the server's, there is no JavaScript and a strict Content-Security-Policy, and everything members wrote is HTML-escaped. The owner's panel shows every message in the fleet; the director's shows its own and the broadcasts.

**Limits.** Rate limits per address (logins, charged once each at their challenge; sign-ins; the servers' key proofs after a lost connection, with a generous limit of their own) and per member (requests, messages, orders, questions, reports), at most 3 open polls per member, requests up to 64 KiB (orders and reports with files up to 24 MiB), messages up to 8000 characters, instructions up to 20,000, names 2-32 characters, the files of one order and of one report up to `max_order_bytes` / `max_report_bytes` (4 MB each), all files kept on the server up to `storage_mb` (2000), unfinished orders up to `orders_open_max` (1000), the lobby up to `lobby_max` (200), the fleet up to `members_max` (1000); too much gets HTTP 429 with Retry-After, 413 or 507. The server refuses everything members upload (messages, orders, files, patches, reports, questions, answers, what they say about themselves) that looks like a secret, with the same patterns as the client (it cannot know the client's own keys, which the client refuses too), and files whose names look like secrets files.

### Running it on a VPS

Requirements: Python 3.10+, and `starlette`, `uvicorn` and `cryptography` (`uv run hub_server.py ...` installs them; the MCP SDK already brings starlette and uvicorn). The server listens on **127.0.0.1:8780** and refuses any other address unless it serves TLS itself (`--tls-cert` and `--tls-key`) or you add `--behind-proxy --insecure-plain-http` for a TLS proxy on another machine of a private network (loudly warned). The usual setup is a TLS reverse proxy on the same machine, such as Caddy (automatic HTTPS certificates):

```
# as root, once
useradd --system --home /var/lib/agent-hub-server --create-home agenthub
mkdir -p /opt/agent-hub && cp hub_server.py /opt/agent-hub/
python3 -m venv /opt/agent-hub/venv && /opt/agent-hub/venv/bin/pip install starlette uvicorn cryptography
sudo -u agenthub AGENT_HUB_SERVER_HOME=/var/lib/agent-hub-server /opt/agent-hub/venv/bin/python \
    /opt/agent-hub/hub_server.py owner init --name "My fleet" --public-url https://hub.example.com
```

`/etc/caddy/Caddyfile` (Caddy gets and renews the certificate, and passes the client's address in X-Forwarded-For, which the server believes only from 127.0.0.1 with `--behind-proxy`; the keep-alive to the server stays below its own 5 seconds, so Caddy never reuses a connection the server just closed; HSTS keeps browsers on https):

```
hub.example.com {
    header Strict-Transport-Security "max-age=31536000"
    reverse_proxy 127.0.0.1:8780 {
        transport http {
            keepalive 4s
        }
    }
}
```

A server that serves TLS itself (`--tls-cert`/`--tls-key`) sends that HSTS header by itself; the members' clients drop an idle connection after 4 seconds, before the server's own 5-second keep-alive closes it, so no request goes out on a connection the server is closing.

`/etc/systemd/system/agent-hub-server.service`:

```
[Unit]
Description=Agent Hub fleet server
After=network-online.target
Wants=network-online.target

[Service]
User=agenthub
Group=agenthub
Environment=AGENT_HUB_SERVER_HOME=/var/lib/agent-hub-server
ExecStart=/opt/agent-hub/venv/bin/python /opt/agent-hub/hub_server.py serve --behind-proxy
Restart=on-failure
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ReadWritePaths=/var/lib/agent-hub-server

[Install]
WantedBy=multi-user.target
```

Then `systemctl daemon-reload && systemctl enable --now agent-hub-server caddy`. Firewall: only SSH and the web ports are open; 8780 stays closed (it listens on 127.0.0.1 anyway):

```
ufw default deny incoming
ufw allow OpenSSH
ufw allow 80,443/tcp
ufw allow 443/udp            # optional: HTTP/3 (without it Caddy falls back to TCP)
ufw enable
```

Run the owner commands as the service user (`sudo -u agenthub AGENT_HUB_SERVER_HOME=/var/lib/agent-hub-server /opt/agent-hub/venv/bin/python /opt/agent-hub/hub_server.py owner ...`). First director: create an invite (`owner invite`; the link carries the server key's fingerprint), let the future director's agent join with it, compare its fingerprint or phrase with them, then `owner director <name>`. **The server's key** (`server.key` in its home, made by `owner init`, or at the first start of a server set up with 2.0.0) is what members pin: back it up with the database; if it is lost, every member's client refuses the new one until its human re-pins it (`agent_hub.py fleet pin`, comparing with the fingerprint you give them from `owner key`; their agents cannot). After updating a 2.0.0 server, members who joined before also pin it once (their client tells them how). Dispatch approvals given under 2.0.0 are bound to their orders' content as it is at the update (audited). The server must know its public URL (`--public-url`, or `owner init --public-url`): members sign for that origin only. For local experiments, `python hub_server.py serve` (no proxy) answers at `http://127.0.0.1:8780`, and agents may use plain http only for 127.0.0.1. A server with a self-signed certificate: `AGENT_HUB_FLEET_CA=/path/ca.pem` on the agents' side (TLS is never switched off).

**What the server keeps.** Its key (`server.key`, owner-only) and its database (`server.db` in its home, owner-only; its schema is versioned and migrated by itself when you update `hub_server.py`, and a database from a newer version is refused) holds members (keys, names, what they said about themselves, the address they joined from), token hashes, events and messages for 30 days, invites (hashed tokens), orders with their history, questions and answers, reports, the files of orders and reports (deleted 30 days after an order is finished; its history stays), handovers with their signatures, and the audit log, unencrypted: whoever runs the server can read the fleet's messages and the shared files (the hidden names and your project folder never reach it). Do not send anything through a fleet that its owner and director should not see.
